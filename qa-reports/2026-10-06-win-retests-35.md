## Votes

- **Q89: 1.** Measured this run on Windows 11 25H2 26200 (Japanese):
  - `cmd /S /C "nosuchprog-xyz"` exits **1**, and so does `cmd /S /C "nosuchprog-xyz C:\x.txt"`.
  - `cmd /S /C "nosuchprog-xyz & exit"` exits **9009**.
  - So `cmd` does set `ERRORLEVEL` to 9009, but `/C` with a lone unknown command hands back 1. The 9009 that
    `exec.rs:341` waits for only comes out when something runs after the failure.

    now this).
  - The PATH walk in `missing_program` is the real evidence that the program is missing, and it already keeps
    builtins like `type` out.
  - Option 2's "exit 1 with empty stdout" would add a second, weaker guess on top of that.

### Proposals

1. **Spread `<Drag:…>` over frames.** Send `PointerMoved(a)` and the press in one frame, then the moves in the next
   few, then the release in a later one. That is the shape egui's drag detection needs.
   - It also needs at least one move past egui's drag threshold in a frame after the press.
   - `Press::Drag` could become a short sequence of sub-steps, the same way `<Wait:>` already holds frames.
   - Without this, 1.11-1.11c and any other drag row stay hand-only.
2. **Write the v0.78.146 behaviour into 23.6** (finding 2). Suggested text: "…a name that is not there opens the folder
   above with the cursor on the nearest name (`zoom-mee.png` → `zoom-me.png`), and the red toast…". The run above can
   serve as the first re-test once the row says so.
3. **Say in 19.4 (or in the `--keys` help) that `<Wheel:N>` with N > 1 is one event, not N notches.** The pane reads
   the smoothed delta, so `<Wheel:2>` moved 4 lines where two `<Wheel:1>` moved 2. The next run that counts notches
   with a single step would report a false failure.
