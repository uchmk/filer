## 見つけたこと

### 1. 16.3 の「`<Enter>` でその位置へ飛ぶ」は、Word の文書では成り立たない（行の文言）

`ja-long.docx` のアウトラインで `3/10 第 2 章 (line 53)` にカーソルを置いて `<Enter>` を押すと、
filer は**ファイルをオープナーに渡す**:

```
WINWORD.EXE /n "C:\…\fx\t16\ja-long.docx"      （Win32_Process の CommandLine）
a.done の toasts: $ start "" "C:\…\fx\t16\ja-long.docx"
```

Word は行番号を取らないので、開くのは文書の**先頭**で、第 2 章ではない。`app.rs` の
`feed_outline_key` を読むと `Act::Open` は `outline_source_line` を `open` に渡しているだけで、
行を活かせるかはオープナー次第（22 節のエディタはそれで飛ぶ）。つまり:

- 「見出しがアウトラインになる」半分は**出る**（上の表）。
- 「`<Enter>` でその位置へ飛ぶ」半分は、**`.docx` では原理的に出ない**。アウトラインの中で
  実際に「その位置へ飛ぶ」のは `j` / `k`（`Act::Arrow`）で、プレビューがその行まで動く。

行を 2 つに割るのが正しいと思う（提案 2 も参照）。割るまで 16.3 は `[ ]` のままにした。

### 2.（所見・誤報を避けるため）`filer env` の `Adapter` は **前の run** の値

走らせた直後に `filer env` を読んだとき `Adapter : …(Dx12, IntegratedGpu)` と出て、
「v0.75.0 で Windows の既定は GL のはずなのに」と一瞬読み違えた。実際にはこの行は
`Last run` の節の中にあり、**そのときの最新は古い run** だった。この run のあとに読み直すと
`D3D12 (Qualcomm(R) Adreno(TM) X2-90 GPU)   (Gl, Other)` で、`last-run.toml` も `backend = "Gl"`。
**既定は GL で正しい**（アダプタ名が `D3D12` なのは GLon12 で、#244 が ARM64 で見たとおり）。
バグではないので finding ではないが、`Last run` の見出しの下にあることが見落としやすい（提案 3）。

### 3. 種を作るとき、自分の誤りで空の `.docx` を作って「プレビューが真っ白」と読みかけた

最初の `make-office.ps1` は Word COM の `Paragraphs.Add()` + `Range.Text` で段落を足していて、
できたのは**段落 1 つの空文書**だった（`word/document.xml` が 3060 バイト、`<w:t>` が 0 個）。
filer のプレビューは空で、`<S-Tab>` は `No outline for this file` と言った。**これは filer ではなく
種の誤り**で、`Selection.TypeText` に直したら上の結果になった。報告に残すのは、
「真っ白なプレビュー」を finding に書く寸前だったから — 種が正しいことを zip の中身で
確かめるまでは、プレビューの空白は filer の答えとは限らない。

## Proposals

### 1. `seek top` / `seek bot` に既定のキーを付ける（1 行）

**何に当たったか**: 16.11 の注記はプレビューの**最後の行の下**にある。プレビューを端まで
送る既定のキーが無く、あるのは `<A-j>` / `<A-k>`（`seek ±5`）だけなので、4000 行のブックでは
**797 回**押すことになる。測るために scratch の keymap で `<A-b>` に `seek bot` を足した。

**どう変えるか**: 一覧の `gg` / `G` に合わせて、プレビューにフォーカスが無くても効く
`<A-g>` = `seek top`、`<A-S-g>` = `seek bot` を既定に入れる（`cmd.rs` は `seek top` / `seek bot` を
もう解釈する。足りないのは束縛だけ）。

**なぜ**: 長いファイルの末尾は、プレビューが「全部読んだのか、途中で切ったのか」を言う場所。
そこへ行けないと、filer が一番伝えたい一行が一番遠い。テストの道具としても毎回同じ細工が要る。

**大きさ**: `defaults/keymap.toml` に 8 行（キーの選択は持ち主の領分なので、QUESTIONS.md 向きかもしれない）。

### 2. アウトラインの `<Enter>` を、行を取れないオープナーのときだけ言う（関数 1 つ）

**何に当たったか**: finding 1。`.docx` のアウトラインで `<Enter>` を押すと Word が先頭を開く。
押した側は「第 2 章へ飛ぶ」つもりでいる。

**どう変えるか**: `feed_outline_key` の `Act::Open` で、`exec::at_line` がそのオープナーに
行番号を渡せたかどうかは既に分かっているはずなので、渡せなかったときだけトーストで
`Word は行番号を取らないので先頭から開きます` のように言う。あるいは `<Enter>` を
「プレビューをその行へ送る」に寄せ、ファイルを開くのは `o` に残す。

**なぜ**: 今は押した結果が「飛んだ」のか「ただ開いた」のか画面から区別できない。
TESTING.md 16.3 の文言が割れているのも同じ原因。

**大きさ**: 前者は関数 1 つ。後者はキーの意味を変えるので設計の問題。

### 3. `filer env` の `Adapter` に、どの run のものかを 1 語足す

**何に当たったか**: finding 2。`Last run` の節の中にあるのに `Adapter` とだけ書いてあるので、
いま走っている filer の話に読める。実際に一度読み違えた。

**どう変えるか**: ラベルを `Adapter (last run)` にするか、`Started` を `Adapter` の**上**に出す。
`Backend` の行（`[ui] backend = "auto"`）は今の設定、`Adapter` は過去の実績、と性質が違うので、
同じ語感で並んでいるのがそもそもの元。

**なぜ**: この欄は 47.x のほぼ全部が根拠にしている欄で、読み違えると run まるごとが嘘になる。

**大きさ**: `envreport.rs` の 1 行。

### 4. `FILER_KEYS_DONE` に「キーがどこにあるか」の行を足す（`focus: list` / `pane` / `outline` / `overlay`）

**何に当たったか**: 1.37 の「The keys are in the pane」を確かめるために、ペインで

**どう変えるか**: `state_report` に `focus:` を 1 行。値は `list` / `pane` / `outline` / `overlay`。

**なぜ**: ペインに関わる行（1.x、19.x、25.x、30.x、40.x）はどれも最初にこれを確かめたい。
いまは全部が同じ回り道をしていて、回り道のほうが壊れやすい。
