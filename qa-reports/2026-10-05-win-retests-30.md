So: `>` (r1), `|` (r2), `<` and `&` (r6), `;` (r7) and the blocking `:` (r8) all leave the path off;
a placeholder still gets it, with or without an operator (r3, r4); a line with neither still gets it at
the end as before (r5). On v0.78.84 (#270) r1 gave `hello  "R:\…\a.txt"` in `out.txt`; now `hello ` alone.
r8's console stayed at `pause` (what `:` is for); it was stopped by its PID 45992 from `launched:`.
The toasts read `$ <the line as run>` in every case.

## Proposals

1. **Say when the path was left off.** r1 and r5 differ only in whether the path is on the end, and the
   toast (`$ echo hello >out.txt` against `$ echo hello "…\a.txt"`) does not say why. Someone used to the
   path being appended (it was until v0.78.91) types `;7z a x.zip >log.txt` and gets a zip of nothing with no
   hint. The toast should add `(no path: the line has a shell operator; use %* to place it)` when the rule
   fired. Why: the rule is invisible otherwise, and `%*` is the fix the user needs to learn. Size: a line or
   two where `substitute_line` decides.
2. **`;` is not an operator to `cmd.exe`.** r7 ran `echo a;b` and `cmd` printed `a;b`: on Windows `;` inside
   a line is ordinary text (an argument delimiter at most), not a command separator, yet it turns the path
   off. A line like `;rg foo;bar` loses the path with no operator in sight. On Windows (shell `cmd /S /C`),
   leave `;` out of the operator list; keep it for `sh -c`. Why: fewer silent surprises; costs one
   `cfg!(windows)`. Size: a line, but it changes the voted rule (Q82 option 1 named `;`), so the owner or
   the vote should confirm.
