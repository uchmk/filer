### 見つけたこと

#### 1. `.pdf` の既定アプリは 0.73.75 でも解決しない。**しかも `.html` も同じ**で、機械側の関連付けが空

このレーンの 0.54.3 の run が「トーストも出ないまま何も起きない」、0.67.2 の run が
「`.pdf` の `UserChoice` ひとつが壊れている（`MSEdgePDF` が解決できない）。filer の外でも同じ」と書いた件を、
0.73.75 で追い直した。**まだ直っていない。新しく分かったのは、壊れているのが `.pdf` 1 つではないこと**
（`.html` の `MSEdgeHTM` も同じ）**と、機械側（`HKCR`）の関連付けがそもそも空であること**。

```text
HKCU:…\FileExts\.pdf\UserChoice\ProgId  = MSEdgePDF     （Hash = K7ZHTuSK6ms=）
HKCU:…\FileExts\.html\UserChoice\ProgId = MSEdgeHTM
HKCR\.pdf の (default)                   = （無い）      ← 機械側の関連付けが空
HKCR\.pdf\OpenWithProgids                = （無い）
HKLM\SOFTWARE\Classes\MSEdgePDF\shell\open\command
  = "C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe" --single-argument %1   （exe は実在する）

filer の「既定アプリ」で .pdf   -> トースト `$ start "" "…\doc.pdf"`、そのあと OpenWith.exe が 1 つ。msedge は 0
cmd /c start "" "…\doc.pdf"     -> OpenWith.exe が 1 つ。msedge は 0
Invoke-Item "…\doc.pdf"         -> 同じ
filer の「既定アプリ」で .html  -> OpenWith.exe が 1 つ
cmd /c start "" "…\page.html"   -> OpenWith.exe が 1 つ        ← filer を通さなくても同じ
cmd /c start "" "…\pic.png"     -> Photos の窓が `pic.png`     ← AppX の ProgId は解決する（対照）
```

つまり**壊れているのは `MSEdge*` の ProgId**（`.pdf` と `.html` の両方）で、`AppX…` の ProgId は無事。
**filer は正しいコマンドを投げていて、シェルがそれを捌けていない。**

**行のほうを直すべきだと思う**（持ち主の判断）。37.8 は「6 項目それぞれが表示どおりに起動する」を
1 つの箱で聞いているので、**この機械では関連付けが直るまで、x64 では持ち主の Chrome が止まるまで、
どちらも `[ ]` のまま**になる。提案は「Proposals」の 1 番に書いた。
なお、関連付けを直すのは持ち主の機械の設定なので、この run は**何も書き換えていない**
（レジストリは読んだだけ）。

#### 2. TESTING.md 37.7 の「started directly」は、実際と違う

- **どこ**: TESTING.md 37.7 の Expect ——「`Win32_Process` shows `sakura.exe` **started directly**, with no `start` and no extra console」。
- **実際**: `block = false` のオープナーは**どれも `cmd /S /C` を通る**。フルパスのオープナーでも
  `"cmd" /S /C ""C:\Program Files (x86)\…\msedge.exe" "…\doc.pdf""` が立ち、その子がプログラム。
  コンソールの窓は出ない（可視の窓の差分で確かめた）。
- **なぜ気になるか**: 「directly」を字面どおり取ると、この行は**通っているのに落ちているように読める**。
  この run は「`start` を通らない・コンソールの窓が増えない」と読み替えて `[x]` を据え置いたが、
  次に読む者が同じ読み替えに至る保証は無い。
- **直し方（持ち主・マージする側へ）**: Expect を
  「`Win32_Process` shows the program itself with the file as its one quoted argument, launched through
  `cmd /S /C` with **no `start` in the line** and no console window of its own」のように、
  `start` の有無とコンソールの窓の有無で書く。**行番号は変えない。**

#### 3. `Start-Process -Wait` は**子孫の終了も待つ**ので、プログラムを起動する行では返ってこない

役割定義の「**Start each `--keys` run with `Start-Process -Wait`**」（#225）をそのまま使ったら、
Edge を開く run が **180 秒のタイムアウトまで返ってこなかった**。filer 自身は 10 秒ほどで終わっていて
（`FILER_KEYS_DONE` に `quit: yes` / `keys: done`、`Get-Process filer` が 0 件）、待っていたのは
**filer が起動した Edge**。`-Wait` はプロセスとその子孫を待つ。

この run の残りは `$p = Start-Process -PassThru …; Wait-Process -Id $p.Id -Timeout 90` に替えて通した。
**オープナー・エディタ・ブラウザを起動する節（22 / 26 / 32 / 37、`<F12>` の行）では `-Wait` は使えない。**
役割定義に 1 行の但し書きが要る（Proposals の 2 番）。

#### 4. Chrome の「窓を閉じる」は、**同じ窓にあった前の run のタブも一緒に閉じる**

37.8 の Chrome の項目を押したあと、`Get-Process chrome | Where MainWindowTitle -eq 'doc.pdf - Google Chrome'`
の `MainWindowHandle` に `WM_CLOSE` を送って片付けた。**Chrome は既存の窓に新しいタブで開く**ので、
消えたのはタブ 1 つではなく窓 1 つで、**同じ窓にあった前の run の `New issue` のタブも一緒に消えた**
（#226 が「4 つ残っていた」と書いた類のもの。この run の開始時点で 1 つ残っていた）。

持ち主の作業が消えたわけではない（残っていたのは前の run のゴミ）が、**狙ったものだけを閉じたとは言えない。**
役割定義の #226 の指示は「タブを数えて、開いたものをタイトルで閉じる」だが、**`Get-Process` の
`MainWindowHandle` は 1 プロセス 1 窓しか見せない**ので、タイトルで選んだつもりが窓ごとになる。
タブを閉じるなら `<C-w>` を**その窓を前に出してから** `SendInput` で送るしかない。Proposals の 2 番に足した。

#### 提案 3: ピッカーの項目に「そのプログラムが無い」ことを出す

- **何に当たったか**: `O` のピッカーは、**入っていないプログラムの項目を、入っているものと見分けなく並べる**。

  エディタの項目を**押すまで見分けられない**（この機械はサクラが無く、x64 には入っている。

- **どう変えるか**: ピッカーを作るときに各項目の先頭の語を 1 回だけ解決し（`PATH` と `App Paths`、

- **大きさ**: 関数 1 つ（`exec.rs` に解決の判定、`app.rs` のピッカー組み立てで `details` に足す）。
  **オープナーの数だけ `PATH` を引く**ので、ピッカーを開くたびのコストは測ったほうがよい。
