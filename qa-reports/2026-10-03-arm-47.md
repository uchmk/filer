## 測り方

47 節の期待値はすべて `(Get-Process filer).CPU` の差なので、1 行 1 プロセスで測る
`measure.ps1` を書いた（証拠フォルダに置いてある）。各回がやること:

1. 残っている `filer.exe` と `.scr`（スクリーンセーバー）を止める（`SPI_SETSCREENSAVEACTIVE` も呼んでいるが、
   この機械では通らない。所見 1a）。
2. `filer.exe <fixture>`（必要なら `--keys`）を `Start-Process` で起動。`--keys` なら `FILER_KEYS_DONE` が出るまで待ち、その中身を全部記録。
3. **10 秒放置**してから `CPU` を読み、`Stopwatch` を回して **10 秒後**にもう一度読む。経過秒も記録する。
4. 読みの前後で入力デスクトップ・スクリーンセーバー・`.scr` プロセスを記録（セーバーが窓を覆うと再描画が減り、
   0 が「通った」ように見えてしまうため。この run で実際に 1 回動いていた。下の所見 1）。

fixture は `scratch\s47`（ファイル 6 個・サブフォルダ 4 個）。47.2 / 47.3 は
**ファイルの下にフォルダが来る並び**が要るので、この run だけの
`FILER_CONFIG_HOME`（`scratch\cfg47\yazi.toml` に `[mgr] sort_dir_first = false` だけ）を当てた。
並びは `--keys` で確かめてある:

- `--keys "<Wait:200>"` → `hovered: …\00-aaa.txt`（ファイル）
- `--keys "j"` → `hovered: …\01-file.txt`（ファイル）
- `--keys "j<Now>j"` → `hovered: …\02-dir`（**サブフォルダ**）

つまり `j<Now>j` は 47.2 の文言そのまま（「`j` でファイルに乗り、すぐ `j` でサブフォルダに乗る」）で、
`<Now>`（v0.65.0）は `App::settled()` を待たずに次を入れるので、40 ms のデバウンスの内側に入る。

## 所見（findings）

### 1. この機械のタスク スケジューラは v0.51.1 の `auto-wintest.ps1` を回している

**見たこと**: 実行の冒頭で入力デスクトップが `Default` ではなく **`Screen-saver`**、
`SPI_GETSCREENSAVERRUNNING` が **True**、`C:\WINDOWS\ASUS\ScreenSaver\OLED Care Screensaver.scr`
（pid 8296）が **17:45:08 から**生きていた。この run が始まったのは 19:17 なので、
**役割定義の言う「実行の間はスクリーンセーバーを止める」（v0.64.3）が働いていない。**

**なぜそうなるか**:

```
Get-ScheduledTask filer-auto-wintest-arm → -File C:\dev\filer\scripts\auto-wintest.ps1 -Lane arm
git -C C:\dev\filer log --oneline -1   → 0a2209f v0.51.1: Take in #80, the first unattended Windows run
```

タスクが読む `C:\dev\filer` は **v0.51.1 に止まった checkout** で、`auto-wintest.ps1` の
ハッシュも worktree のものと違う（`414EBD89…` 対 `EA213041…`）。`Suspend-ScreenSaver` も
`Stop-ScreenSavers` の見張りもこの版には無いので、`%LOCALAPPDATA%\filer-wintest\` には
走行中に出るはずの `screensaver-arm.json` も無く、ログにも
`Holding the screen saver off for the run` が一度も出ていない（17:17 の run も同じ）。

**何が危ないか**: この run は `--keys`（プロセス内でキーを入れる）だけで測ったので無害だったが、
**`SendInput` を使う行（19 節のホイール、14 節のクリック、2.6、3.4〜3.7）はこの状態だと
「成功を返して何も届かない」**。#88 がまさにそれで、気づかないまま `[x]` が付く形。
v0.73.17 の `target` を RAM ディスクへ逃がす処理も、同じ理由でこのレーンでは一度も動いていない。

**直し方（持ち主の作業）**: `git -C C:\dev\filer pull`（または `git -C C:\dev\filer checkout main &&
git pull`）で launcher を今の `main` に上げる。worktree 側は `origin/main` から作られるので
常に新しく、**launcher だけが古い**。この run では測定のたびにこちらで `.scr` を止めてから測った
（各測定のログの `stopped a running screen saver:` の行）。

### 1a. この機械では `SystemParametersInfo(SPI_SETSCREENSAVEACTIVE)` が通らない（エラー 329）

ついでに分かったこと。測定の前にセーバーを無効化しようとしたが、**この機械では
`SPI_SETSCREENSAVEACTIVE` が false でも true でも `FALSE` を返し、`GetLastError` = **329**
（`An operation is currently in progress with the device.`）**。`fWinIni` を 0 / 2 / 3 に変えても同じ。
`SPI_GETSCREENSAVEACTIVE` は（レジストリの `ScreenSaveActive` が 1 なのに）`False` を返し続ける
— ASUS 側のソフトが握っていると思われる。

つまり `auto-wintest.ps1` を新しくしても、この機械で効くのは
**`Stop-ScreenSavers`（`.scr` を 5 秒おきに殺す見張り）だけ**で、`Set-SaverActive` は無言の空振りになる
（`$false` を返すので見れば分かるが、`[void]` で捨てている）。`Resume-ScreenSaver` の「戻した」も
同じく空振り。**結果としてレジストリも実際の設定も変わっておらず、この run は何も戻す必要が無かった。**

## Proposals

### 提案 1: `FILER_KEYS_DONE` に「描いたフレーム数」を足す

**踏んだこと**: 47 節の 5 行は全部「放置した窓が描き続けていないか」なのに、外から取れる数字は
`(Get-Process filer).CPU` しか無い。これは起動・トーストの消え際・測定が混ざった値で、
分解能も Windows のスケジューラの刻み（約 15.6 ms）だから、47.2 の **0.016 s は「1 刻み」で、
「何もしていない」と区別が付かない**。だから今回は正の対照（100 ms ごとのキーで 1.203 CPU-s/10 s）を
別に取らないと、0 が「測れている 0」だと言えなかった。

**どう変えるべきか**: `state_report`（`src/main.rs`）に `frames: <起動からの描画回数>` を 1 行足す。
`eframe` の update を数えるだけのカウンタでよい。あれば 47.1〜47.3 は
「10 秒の間に**フレームが 0 枚**」と言える。これは v0.54.2 が直したこと（デバウンスのタイマーが
残って 60 fps で描き続ける）そのもので、CPU の差より近い。

**なぜ**: 今の形だと、再発したときに「0.016 s は刻み 1 つか、2 回だけ描いたのか」が分からない。
フレーム数なら 1 枚でも分かる。測定の時間も 10 秒要らなくなる。

**大きさ**: カウンタ 1 つと 1 行。`--keys` を使う他の節（19 節の `preview top` と同じ使い方）にも効く。

### 提案 2: `<Shot:name>` と同じ形で、途中の状態を書き出す `<State:name>` が欲しい

**踏んだこと**: 47.2 で欲しかったのは「キーの直後の状態」と「10 秒後の状態」の 2 つ
（何も触っていないのに `preview top` やトーストが動いていないことまで言えると、CPU の 0 の裏付けになる）。
`FILER_KEYS_DONE` はスクリプトの終わりに 1 回だけ出るので、前者しか取れない。
`--keys "j<Now>j<Wait:10000>"` にすれば 10 秒後の状態は取れるが、そうすると
**キーの直後の状態が消える**。2 回起動して比べるのは、同じ run の比較にならない。

**どう変えるべきか**: `<Shot:name>`（v0.67.0）と同じ場所・同じ命名で、`state_report` を
`name.txt` に書く `<State:name>` を足す。`--keys "j<Now>j<State:after><Wait:10000><State:later>"` が
1 回の起動で済む。

**なぜ**: 画面は 1 run で 2 枚撮れるのに、**読める文字の状態は 1 回しか取れない**という非対称が、
47 節に限らず「前と後」を見る行（19 節のホイール、3 節のズーム）で毎回 2 回起動を強いている。

**大きさ**: `<Shot:>` の実装の隣に関数 1 つ。キー script の構文は増やさない形。

### 提案 3: `auto-wintest.ps1` は自分の commit をログとプロンプトに出すべき

**踏んだこと**: 所見 1。launcher が v0.51.1 のままだったことは、**スクリーンセーバーが動いている**という
副作用から逆算して気づいた。ログには「起動した」しか出ないので、無人の run は
自分が古い launcher から呼ばれたことを知る手立てが無い。

**どう変えるべきか**: 起動時に `git -C <スクリプトの checkout> rev-parse --short HEAD` と
`git describe --tags` をログに書き、プロンプトの末尾にも 1 行入れる（「この run の launcher は
`0a2209f` / `main` より N commit 遅れ」）。遅れていたら `Say` で警告する。

**なぜ**: launcher は worktree と違って自動で更新されないので、**黙って古くなる唯一の部品**。
今回はセーバーだけで済んだが、`-Lane arm` の挙動や scratch の決め方もこのスクリプトの中にある。
報告に 1 行出ていれば、マージする側が `git pull` を促せる。

**大きさ**: スクリプトに数行。
