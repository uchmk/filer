## Findings

1. **TESTING.md 21.14 cannot be followed key-for-key since v0.78.5** (above). Pressing `E` three
   times in a row packs each archive into the next, because the cursor follows the file `E` made.
   The run has to press `gg` between them. Either the row should say so or `E` should not move the
   cursor off a folder it packed. Not a crash, and the archives it produced were valid — but a run
   that trusted the toast line (`Packed into to-pack.tar.gz`) and not the listing would have ticked
   the row on three nested archives.

2. **`E`'s prefilled name is always `{stem}.zip`.** Packing as anything else costs `<End>` plus four
   backspaces plus the extension — five keys before the name. On the third press of the broken run
   the prefill for `to-pack.tar.gz` was `to-pack.tar.zip` (`.gz` alone counted as the extension), so
   the same five keys produced `to-pack.tar.7z`. Correct, but surprising.

No crash, no hang, no stalled `--keys` file: all 16 `--keys` runs in this session ended with
`keys: done` as their last line (checked over the kept `FILER_KEYS_DONE` files, 0 otherwise), and
none vanished without writing one.

## Proposals

### 1. `E` should leave the cursor on what it packed, not on the archive

- **What I ran into**: `--keys "E<Enter><Wait:2500>E<End>…<Enter>"` on a folder made
  `to-pack.zip`, then a `.tar.gz` **of that zip**, then a `.7z` of the `.tar.gz`. Each toast said
  `Packed into …`, so nothing on screen said the second press had a different target.
- **What should change**: after a `Compress` job, keep the cursor on the source when there was one
  and it still exists; land on the archive only when the source is gone. (v0.78.5 made the cursor
  follow a rename or a new file, which is right for `a` / `r` — the thing you just named is the
  thing you want next. For `E` it is the opposite: the folder is still the subject.)
- **Why**: packing one folder in two formats is a normal thing to want, and today the second one is
  silently wrong. It also makes TESTING.md 21.14 unfollowable.
- **How big**: a condition where the compress job's `made` is handed to the cursor (`app.rs` around
  the `OpKind::Compress(_) | OpKind::TakeOut | OpKind::Extract` arm) — a few lines.

### 2. `E` should remember the last format, or offer the three

- **What I ran into**: the prompt always opens on `{stem}.zip` with the stem selected, so the one
  thing you cannot type quickly is the extension. Three formats took `<End><BS><BS><BS><BS>.tar.gz`.
- **What should change**: either prefill with the extension used last (per session is enough), or
  let `<Tab>` in the compress prompt cycle `.zip` → `.tar.gz` → `.7z` in place.
- **Why**: `.zip` is the right default, but anyone who prefers `.7z` retypes it every time, and the
  current selection makes the easy keystrokes edit the half you did not want to change.
- **How big**: a line for the remembered extension; `<Tab>` cycling is a small function in the
  input handler.

### 3. The compare view should have a copy key

- **What I ran into**: 5.9's expectation is a list of paths with `< > ~ =` on them, and the only way
  to get it out of the program is a screenshot. The compare overlay's footer offers
  `n / N · z · Enter · q` and nothing else; spot has `C`, help has `C`, the tree comparison has
  neither.
- **What should change**: `C` (or `y`) in a folder comparison copies the shown rows as text —
  the sign, the relative path, and the sizes — honouring `z` (hide matches) so you copy what you
  see.
- **Why**: a folder comparison is exactly the thing you want to paste into a message or a bug
  report, and the rows already exist as `Outcome::Tree { rows }`. It would also turn 5.9 and most of
  section 45 from "read it off a picture" into text, which is what this whole lane is trying to do.
- **How big**: a formatting function over rows that are already built, plus one keymap entry in the
  `[diff]` section.

### 4. `<State:>` should say whether a minimap strip was drawn, not only whether it is switched on

- **What I ran into**: 16.12 asks for "it scrolls, **and the strip is there**". The scroll is three
  numbers in `<State:>`; the strip is not — the state says `minimap setting: on`, which is the
  setting, and `main.rs` even comments that whether a strip was drawn "is a picture's question". So
  the measurable half of the row was measured and the other half needed `xlsx-p1.png`.
- **What should change**: add a line like `minimap: drawn, band 15-47 of 3984` when the painter drew
  one, and `minimap: not drawn (rendered markdown)` / `(too few lines)` / `(pane too narrow)` when
  it did not — the painter already decides all of this.
- **Why**: it is not a picture's question, it is a question the code answers and then throws away.
  Every minimap row in TESTING.md (2.x, 16.12, 18.x) is stuck as an appearance row for want of one
  line, and this run had to keep a screenshot for something the program knew.
- **How big**: a flag the minimap painter sets on the app, read in `state_lines` — a line in each
  place, and a decision about what to put in the parenthesis.
