### 19.7 — the pointer between panes mid-turn

`many\` (500 entries) in both panes, `--keys '<Wait:1500><C-w>…'` to open the split.
`list top` in `FILER_KEYS_DONE` is the active tab's only, so each case was pressed
twice: once ending on the right pane, once with a trailing `<C-w>` so the file reports
the left. The trailing `<C-w>` only moves the keys; `split:` in the file says which
pane it read (`keys right` / `keys left`).

Calibration first, all on the right pane: a full notch (120) → `list top: 2`; one
quarter (30) → `list top: 0`; two quarters → `list top: 1`. So a quarter is about half
a row, which is what the case needs.

| case | quarter notches, in order | left `list top` | right `list top` |
| --- | --- | --- | --- |
| A | left, right | 0 | 0 |
| B | left, right, right | 0 | **1** |
| C | left, right, **left** | **1** | 0 |

A is "neither jumps": each pane is holding half a row and neither has spent it. B is the
right pane's own two halves adding up, with the left still holding its one. **C is the
case #211 did not press**, and it is the one that names the bug: the left pane's half
survived the pointer leaving for the other pane and coming back, and completed there —
not in the pane that was under the pointer in between. A shared remainder would have
moved the right pane on the third quarter.

### Proposals

1. **`FILER_KEYS_DONE` should print the other pane's `list top` while the view is
   split.** What I ran into: 19.7 is about two panes and the state file reports one —
   `list top` is `app.tab()`'s, so every case had to be run twice, identical except for
   a trailing `<C-w>`, to read both numbers. Six runs for three cases, and the two
   halves of each case come from different processes, which is exactly the kind of
   comparison this file exists to avoid. What should change: when `app.split` is
   `Some`, add one line — `other list top: N` (and the other tab's `cwd`), beside the
   existing `split: yes, keys right`. Why: it halves the runs for every split row and
   makes a single run's two numbers comparable; it costs a reader nothing, since the
   line is absent when there is no split. How big: a few lines in `state_report`.

2. **`toasts:` should carry the `×N`.** What I ran into: 15.4's expectation is
   literally a count on a toast, and the count is the one part of it that is not in
   `FILER_KEYS_DONE` — `toast:` and `toasts:` both print `t.text` and drop
   `Toast::count`. I had to take a screenshot, find it unreadable at 20% scale, and
   re-run the whole row under a 56 px font to make a number legible that the program
   already holds as an integer. What should change: write the live toasts' counts in
   the `toast:` line, as the screen draws them — `toast: Scale 20% (minimum) ×8`. The
   `toasts:` log is a list of raises and is right as it is. Why: it takes the one
   remaining row of section 15 that needed a picture and makes it text; "a held key
   keeps counting after the thing stopped moving" is the distinction v0.57.3 added
   `(minimum)` for, and a checker cannot read half of it without a camera. How big: one
   line, plus carrying `count` into the state report.

3. **`--keys` should be able to press a key N times.** What I ran into: the scripts in
   this run include `'<C-+>'` repeated 45 times by the shell building the string. It
   works, but the script in the report is a wall, and a miscount is invisible. What
   should change: `<C-+>*45`, or `<Rep:45>` applying to the key before it. Why: every
   "hold it down" row in TESTING.md (15.4, 15.8, and the scale rows of 3) is a
   repetition count, and the count is the assertion — it should be readable in the
   script. How big: a token in `keyscript::parse`, and a `Press` that pushes the same
   events N times.

4. **`filer env` should say which pane the keys are in, or rather: there is no way to
   ask a running filer anything.** What I ran into: everything I wanted mid-run —
   the other pane's offset, the zoom between two keys — exists only at the end of a
   `--keys` script, so a case that needs two readings needs two processes. What should
   change: a `<Dump:name>` step beside `<Shot:name>`, writing the same `state_report`
   to `name.txt` at that point in the script. Why: `<Shot:>` already settled that
   "the picture between two keys comes from the same run" is worth a token (v0.67.12);
   the numbers deserve the same, and they are cheaper than a picture. How big: a
   `Press` variant reusing `state_report`, about as large as `<Shot:>` was.
