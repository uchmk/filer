## 47.6 — ARM64 で `[ui] backend = "gl"` は GL のアダプタを取れる

順番表の問いは「この機械で `gl` がアダプタを取れるのか、既定に落ちて `no adapter` の警告が出るのか」。
**取れる。** `filer env` の `Adapter` は

```
Adapter       : D3D12 (Qualcomm(R) Adreno(TM) X2-90 GPU)   (Gl, Other)
```

で、`(Gl, …)` で終わる（ANGLE の D3D12 バックエンド経由）。`no adapter` の警告は出ず、`Warnings : none`。

CPU は、起動して（キーがあれば `keys: done` を待って）10 秒置き、`(Get-Process).CPU` を 10 秒あけて 2 回読んだ（`cpu.ps1`）。

| 行 | 設定 | `filer env` の `Adapter` | 10 秒の差 | 一番増えたスレッド |
| --- | --- | --- | --- | --- |
| 47.1（対照、既定） | 無し | `Qualcomm(R) Adreno(TM) X2-90 GPU   (Vulkan, IntegratedGpu)` | **0.000 s** | なし |
| 47.1 | `backend = "gl"` | `D3D12 (…)   (Gl, Other)` | **0.000 s** | なし |
| 47.2（`jjjjj<Now>k`、`hovered: …\fx\to-pack`） | `gl` | 同じ | **0.000 s** | なし |
| 47.3（同じ後に `ShowWindow(SW_MINIMIZE)`、`IsIconic` = True） | `gl` | 同じ | **0.000 s** | なし |
| 47.5（`f`、`overlay: input`） | `gl` | 同じ | **0.000 s** | なし |
| 陽性対照（`j<Wait:100>k<Wait:100>` を 60 回、押している間に読む） | `gl` | — | **2.016 s** | — |

- **ARM64 ではそもそも既定（Vulkan）でも増えない**（0.000 s）。x64 の AMD で 10 秒に 10 CPU 秒使う現象（#207 / #232 / #240）は
  この機械には無い。だから 47.6 の「Vulkan と DX12 では通らなかった 47.1 が通る」という後半は、ここでは比較にならない。
- 陽性対照が 2.016 s と読めるので、0.000 は読みであって計器の故障ではない。
- 47.2 / 47.3 / 47.5 は前から ARM64 の印で `[x]`。GL でも同じ結果であることを確かめただけで、印は触っていない。

run 限りの `filer.toml` に `[ui]` `backend = "directx"`、次に `"metal"`。キーは `<Wait:2000><State:s><Shot:s><Quit>`。

| 設定 | 窓 | `toasts:` | `filer env` の `Adapter` |
| --- | --- | --- | --- |
| `"directx"` | 開いた（`cwd: …\fx`、`k47.7-directx\s.png`） | `Config: [ui] backend = "directx" is not one of auto, vulkan, dx12, metal, gl; drawing with the default` | `Qualcomm(R) Adreno(TM) X2-90 GPU   (Vulkan, IntegratedGpu)` |

行の文言どおり。**`filer env` の `Warnings` はどちらも `none`** — #240 が x64 で見つけた食い違いが ARM64 でも同じように出る（下の所見 1）。

## 所見

1. **`filer env` の `Warnings` に `[ui] backend` の警告が出ない（#240 の所見 1 を ARM64 で再現）。**
   `"directx"`（値が不正）も `"metal"`（アダプタが無い）も、窓のトーストには出るが `filer env` は `Warnings : none`
   （`k47.7-directx\env.txt`、`k47.7-metal\env.txt`）。x64 だけの話ではないので、TODO.md に起こす価値がある。

2. **`No such file or folder: … — showing …` のエラーが、出るときと出ないときがある。**
   26.2 の仕掛けを作るときに当たった。`g<Space>` で「存在するフォルダの下の無い名前」（`..\s26fresh\nosuch-abc123`）へ飛ばすと、
   同じ操作で結果が 2 通りに分かれた:

   - `k26c`: `toasts: No such file or folder: nosuch-abc123 — showing C:\…\s26fresh`（出た）
   - `k26d`: `toasts:` が**空**（出なかった）。`cwd` は同じく `…\s26fresh` に着いている

   読んだ限りでは競争に見える。`cd_inner` は親ペイン用に移動先の親（= `s26fresh`）も走査に出すので、
   その答えが先に返るとキャッシュに載り、`undo_cd` → `cd_failed` → `arrive` の時点で
   `arrive` の `pending.filter(|_| !listed)` が `pending_cd` を捨てる。`reveal` が消えるので
   `app.rs:1785` のエラーに届かない。**「無い名前へ飛んだのに黙って親が出る」**のは、
   このエラー行がもともと塞ぐために足されたはずの穴なので、挙動として安定していないほうが問題。
   26.2 では、必ず失敗する形（ファイルの下: `a.txt\nosuch`）に替えて確かめた。TODO.md 向き。

3. 26.2 の行の手順（`g<Space>` と作った名前）は、所見 2 のとおり**毎回はエラーにならない**。
   行の文言を「ファイルの下の名前（`a.txt\nosuch`）」に替えると確実に再現する。下の Queue に書いた。

### Proposals

3 件。

#### 1. `filer env` に `[ui] backend` の警告を出す（#240 の提案 1 と同じ。ARM64 でも同じ）

- **何に当たったか**: 47.7。`backend = "directx"` でも `"metal"` でも、窓には警告のトーストが出るのに `filer env` は `Warnings : none`。
- **何を変えるか**: 設定を読んだ所で `backend_name()` の `Err` を `warnings` に積む。アダプタが無いほうは
  last-run.toml に起動時の警告を残して `filer env` がそれを出す形でもよい。
- **なぜ**: トーストは数秒で消える。あとから「なぜ GL にならないのか」を調べる唯一の文字の出口が `filer env` で、
  そこが「問題なし」と言う。**2 つのレーンが独立に同じ所でつまずいた**ので、偶然ではない。
- **大きさ**: 不正な値のほうは数行。

#### 2. 無い名前へ飛んだときのエラーを、走査の順番に依らせない

- **何に当たったか**: 所見 2。同じ `g<Space>` の操作で、エラーが出る run と黙って親が出る run があった（`k26c` / `k26d`）。
- **何を変えるか**: `reveal` を `pending_cd` に載せるのをやめ、`arrive` した先の一覧が整った時点で
  「名前が無ければ言う」を 1 回だけ評価する（移動先ごとに 1 つ覚えておく `pending_reveal` のような形）。
  今は `pending_cd` が「まだ一覧が来ていない」の印を兼ねているので、キャッシュに載った瞬間に `reveal` も一緒に捨てられる。
- **なぜ**: 黙って親のフォルダが出るのは、打ったパスがそこにあるように見える。この行（`app.rs:1785`）の
  コメント自身が「それを塞ぐために足した」と書いている。
- **大きさ**: 関数 1 つ分（`arrive` と `cd_failed` の間の受け渡し）。

#### 3. `g<Space>` のプロンプトを、末尾から消しやすくする

- **何に当たったか**: 26.2 の仕掛け。`g<Space>` は `<cwd>\` が入った状態で開くので、**ホームの別の場所**（`C:\Users\…\Documents\…`）へ
  飛ばすには、まず 60 字あまりを消すことになる。`--keys` では消す手段が要るし、人が打つときも同じ。
- **何を変えるか**: プロンプトを開いた直後は、入っている文字を**選択済み**（次の 1 文字で置き換わる）にする。
  ブラウザのアドレス欄や Explorer の `Ctrl`+`L` と同じ振る舞い。足す場合は `<End>` で末尾へ行けばよい。
- **なぜ**: 「ここから下へ潜る」ときは今のままが速いが、「別の場所へ飛ぶ」ときは今の形が一番遅い。
  `g<Space>` の説明は「Jump interactively」なので、後者も主な用途のはず。
- **大きさ**: 入力欄に「全選択で開く」の旗を 1 つ足す。既定をどちらにするかは持ち主の判断（QUESTIONS.md 向き）。
