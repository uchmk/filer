## 1.11-1.11c -- dragging over pane output, with a real pointer

On this machine an absolute `SendInput` move does not move the cursor. Probed this run: `SendInput` returned 1 with the
40-byte `INPUT`, the input desktop read `Default`, and `GetCursorPos` was unchanged. **`SetCursorPos` does move it**
(300,300 read back at once). So `drag.ps1` does the following:

- makes the script per-monitor DPI aware;
- checks that filer's own window (`Window Class`, `Filer: …`) is in the foreground and that `WindowFromPoint` at the
  start lands on it;
- moves the pointer with `SetCursorPos`, in five steps 60 ms apart;
- sends only the button down and up with `SendInput`.

The clipboard was armed with a sentinel before each drag.

The pane is `pwsh -NoProfile` (`FILER_TERM_SHELL` / `FILER_TERM_ARGS`), started by `--keys` with
`<C-t>…cls<Enter>…echo<Space>ABCDEFGHIJKLMNOP<Enter>…<Shot:pane>`. The output line is at y = 845 px in the client.
Cells are 12.75 px wide from x = 9 (from `pane.png`; the pane is at 1.5).

## Findings

1. **Closing the window during a `--keys` run leaves no `FILER_KEYS_DONE` file.** Steps:
   - run `<C-t>…<State:ready><Wait:60000>×6<Quit>`;
   - after `ready.txt` came, close filer's window with `CloseMainWindow` (`WM_CLOSE`).

   The process exited within 8 s, and `R:\…\k111` held only `pane.png` and `ready.txt`: no `keys.done`.

   `windows-role.md` says the file "always comes" (`keys: done`, `keys: stalled`, `keys: panicked`, `keys: refused`).
   `src/main.rs:1030` writes it only when `app.quit` is set (`q`, `<Quit>`); a close from the title bar or `WM_CLOSE`
   does not take that path. A script waiting on the done file then waits for its timeout, and a reader cannot tell a
   closed window from a vanished process.

   - Size: one sentence in the role's table ("a click, a hover, the pointer").
