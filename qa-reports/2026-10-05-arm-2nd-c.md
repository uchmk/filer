### 46.11 in detail, and why the obvious measurement lies

The row says "watch for a console window", which sounds like an eye row. It is not, but the first
measurement I reached for was wrong, and it is worth writing down.

Counting `conhost.exe` processes reads as a **failure**: six spot opens in the repository produced
**21 console-host processes that were not in the baseline**, against **1** in a 30-second control run
with no filer. Chasing their parents explains it — in a 7-second window over three spot opens,
**8 `conhost.exe` processes had a `git.exe` as their parent**:

```
conhost 38272 <- git 38764      conhost 18948 <- git 39288
conhost 39148 <- git 15672      conhost 14296 <- git 35004      conhost 39036 <- git 31572   (+3 more)
```

`CREATE_NO_WINDOW` (which `src/fs/git.rs:380` sets) does not stop the console host being created —
it stops its **window** being shown. So the measurement that matches the row is the set of *visible*
top-level windows of the console classes, sampled while git runs (`flash46b.ps1`, EnumWindows +
IsWindowVisible + GetClassName every 25 ms):

```
six spot opens: 654 samples, 23 of them with a git.exe up, visible console windows = 3
   PseudoConsoleWindow |                      CASCADIA_HOSTING_WINDOW_CLASS | claude
   CASCADIA_HOSTING_WINDOW_CLASS | PowerShell
control (no filer):  626 samples,  0 with git up, visible console windows = 3  (the same three)
```

The three are this session's own terminals, present before and after. **No `ConsoleWindowClass`
window appeared at any sample while git was running.** That is 46.11's claim, measured.

## Proposals

### 1. Spawn `git` with `DETACHED_PROCESS`, not only `CREATE_NO_WINDOW`

- **What I ran into**: measuring 46.11, six spot opens created **21 `conhost.exe` processes** (1 in
  the control run), eight of which I caught with a `git.exe` as their parent. The windows are hidden,
  so the row still passes — but every `git` filer runs pays for a second process.
- **What should change**: add `DETACHED_PROCESS` (0x8) to the creation flags in `src/fs/git.rs:380`
  (and the same three other places, `exec.rs:492`, `fs/ops.rs:950`, `preview/external.rs:93`, where
  the child's output is captured and nothing needs a console). With no console attached at all, no
  console host is created.
- **Why**: it halves the process count of a spot open (22 → 11 here) and of every listing refresh
  the status worker drives. It also makes 46.11 checkable by counting processes — the measurement
  anyone would reach for first — instead of by enumerating window classes, which is what this run
  had to write.
- **How big**: one constant and one `|` per call site, plus a check that nothing in the tree relies
  on the child having a console (`cmd /S /C` in `preview/external.rs` would be the one to look at).

### 2. The Git section should ask git fewer times

- **What I ran into**: the `GIT_TRACE` above — eight git processes for one panel, including
  `rev-parse --show-prefix --abbrev-ref HEAD` twice in the same open and
  `merge-base --is-ancestor` twice, and `config --get remote.origin.url` on every open of every row
  in the same repository.
- **What should change**: cache per repository root, for as long as the directory stays listed, the
  three answers that cannot change under the cursor — the root itself, `remote.origin.url`, and
  `origin/HEAD`. The remaining per-file work is one `log` and the merge lookup.
- **Why**: on this machine a spot open is 100 ms, so this is not about the panel feeling slow; it is
  about holding a key down. Walking a repository with `<Tab>` open re-asks git eight times a row,
  and each of those is a process pair (Proposal 1). A laptop on battery notices.
- **How big**: a small struct behind the git worker keyed by repository root — a function, not a
  design question.

### 3. TESTING.md 46.11 should say what to measure

- **What I ran into**: "Watch for a console window" is the only row in section 46 that does not name
  something readable, and the obvious reading of it (count `conhost.exe`) says the row **fails**.
- **What should change**: rewrite the expectation as "while a `git.exe` of filer's is up, the set of
  visible top-level windows of class `ConsoleWindowClass` does not change", and add the trap in a
  sentence: a `conhost.exe` per `git.exe` is expected, because `CREATE_NO_WINDOW` hides the window
  rather than skipping the console.
- **Why**: the next run to take this row will reach for the process count, see 21 of them, and
  either file a bug that is not one or quietly tick an eye row. The script that does it right is in
  this run's evidence (`flash46b.ps1`) and could be named in the row.
- **How big**: two sentences in TESTING.md. (If Proposal 1 lands, the row becomes a plain process
  count and the trap disappears — then the rewrite is "no new console host, and no visible console
  window".)

### 4. `C` should keep `Came in via`'s two values apart

- **What I ran into**: the clipboard line is `Came in via<TAB>#42  bb23a4e` — one field holding a
  pull request number and a hash, separated by two spaces, inside a format whose whole point is that
  a tab separates label from value. Every row in section 46 that I compared against git had to be
  split by hand.
- **What should change**: either two rows (`Came in via  #42` and `Merge commit  bb23a4e`), or keep
  the panel as it is and make `C` emit `#42<TAB>bb23a4e`.
- **Why**: `C`'s output is the one thing in the Git section a script or a bug report consumes, and
  this is the only field in it that needs parsing. Same shape as #261's proposal 3 (a copy key for
  the compare view): what the panel shows is a layout, what `C` writes is data.
- **How big**: a line in the spot provider, or in `C`'s formatter — but which of the two is a small
  call for the owner, since the panel's own look changes in the first option.
