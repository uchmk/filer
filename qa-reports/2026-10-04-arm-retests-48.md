## Proposals

3 件。

### 1. 不正な `[ui] backend` の警告を、`filer env` と窓で同じ文にする

- **何に当たったか**: 47.7。同じ 1 つの設定ミスに対して、窓のトーストは
  `…; drawing with Gl instead`、`filer env` の `Warnings` は `…; drawing with the default` と、
  **違う文**を出す。両方をこの run で読み比べた（上の表）。
- **何を変えるか**: `filer env` 側も実際に落ちる先を名乗る。`filer env` は窓を開かないので
  その場で解決できないなら、`drawing with the default (auto)` のように **`auto` に落ちると書く**だけでもよい。
- **なぜ**: 47.7 のように両方を読む人は「2 つの別々のことが起きた」と読む。実際は同じ 1 つの判断。
  設定を直す人は `filer env` しか見ないことが多く、そちらだけが古い言い方で残っている。
- **大きさ**: 文字列 1 つ（か、落ちる先を返す関数を 1 つ共有する）。

### 2. `Last run` に、その run の `[ui] backend` を一緒に残す

- **何に当たったか**: 所見 1。`"dx12"` の run の直後に `"directx"` の設定で `filer env` を読むと、
  `Backend : [ui] backend = "directx"` と `Adapter : … (Dx12, IntegratedGpu)` が並ぶ。
  47.6 / 47.7 / 47.8 はこの 2 行を突き合わせる行なので、順番次第で通ってしまう／落ちてしまう。
- **何を変えるか**: `Last run` に `Backend used : gl（[ui] backend = "directx" から）` のような 1 行を足す
  （`Started`（v0.75.7）と同じく、run の側が state に書く）。`Backend` の行は「今の設定」、
  `Last run` の行は「そのとき使われたもの」とはっきり分かれる。
- **なぜ**: いまは `Adapter` がどの設定の結果なのかを**読む側が覚えておくしかない**。
  この run はスクリプトで順番を守ったが、人が手で確かめるときに一番踏みやすい。
- **大きさ**: state に 1 フィールド、表示に 1 行。

### 3. `filer env` の `Config` 欄で、ラベルの桁をパスの長さに引きずらせない

- **何に当たったか**: 所見 2。`FILER_CONFIG_HOME` が 67 文字のとき、`Warnings` の値が 83 桁目から始まり、
  120 桁の窓でも折り返した（`env-directx-full.txt`）。
- **何を変えるか**: 設定フォルダのパスは**自分の行に置き**、その下にファイル一覧を字下げする
  （今の「パス : ファイル」を 2 行に割る）。あるいはラベル桁に上限（30 桁ほど）を置き、
  超えるパスだけ折り返す。
- **なぜ**: `filer env` は「人が読んで貼る」ための出力で、`FILER_CONFIG_HOME` を使うのは
  まさに不具合を切り分けている人（この run のような）。一番要るときに一番読みにくい。
- **大きさ**: 整形の関数 1 つ。
