## Findings

**1. `<Tab>` cannot cycle through the hits of a completion.** `sub<Tab><Tab>` on a directory
holding `subdir-one\` and `subdir-two\` gave `subdir-one\` both times (run d), never
`subdir-two\`. `apply_completion` keeps `completion_at` for the next press, but the first
completion appends a `\`, so `completion_target` now points at `subdir-one` with an empty
prefix and the cycle is lost. Nothing in TESTING.md asks for cycling, so this is not 23.4
failing — but the code plainly means to offer it (`completion_at = idx + 1`, `% hits.len()`),
so one of the two is wrong.

**2. `SendInput` returned success and reached nothing** (the #211 / #88 pattern, again on
this laptop). After `<F12>` I tried to close the tab it opened: the foreground window was
verified by handle as `New issue - Google Chrome`, `SPI_GETSCREENSAVERRUNNING` was false,
and `SendInput` returned 4 for a `Ctrl`+`W` — twice, the second time with scan codes in
`wScan` as the role asks. The tab is still open. **The bug-report tab `<F12>` opened is left
in the owner's Chrome**; I did not keep trying, because blind keys into someone's browser
cost more than the tidy-up is worth. A later run should not treat a non-zero `SendInput`
return as proof the key arrived.

## Proposals

**1. `--keys` needs a way to quit with an overlay open.** Every run above had to end with the
prompt open, because `input:` is only written while one is (`main.rs:1030`). A trailing `q`
would be typed into the field, so there is no way to say "quit now": filer sits on screen
until something outside kills it. Each of the six runs needed a `Start-Process` + poll for
`FILER_KEYS_DONE` + `Stop-Process` wrapper, and the first attempt — a plain foreground call —
hung until a 300 s tool timeout. **What should change**: a `<Quit>` token in a `--keys`
script that quits from wherever the app is, after the report is written, the way a trailing
`q` does for the list (v0.72.8). **Why**: every row whose expectation is an open overlay
hits this, and the workaround is per-caller shell code that is easy to get subtly wrong.
**Size**: a token in `keyscript.rs` and one branch in the script runner.

**2. Make `<Tab>` cycle, or stop pretending it does.** Finding 1. **What should change**:
keep the cycle alive while the field still holds exactly what the last completion wrote, so
`<Tab><Tab>` steps `subdir-one\` → `subdir-two\`; or, if cycling is not wanted, drop
`completion_at`. **Why**: on a share, listing again to try the next name costs the round
trip the completion just paid for, and a directory full of `2026-10-0x-...` names is where
you most want the second press. **Size**: a few lines in `complete_input` / `apply_completion`.

**3. A pending completion should say more than eight pixels.** On the dead host the `<Tab>`
sat for ~42 s and the only difference on screen was the `…` at the far right of the prompt
row — I had to diff pixel maps against a control frame to be sure it was there at all, and
that is after v0.73.52 made it the accent colour. filer already has a place for work that is
taking a while: the Tasks panel. **What should change**: a completion still pending after a
second or two gets a Tasks row (`cd completion: \\host\share`), and one that fails says so in
a toast instead of ending in silence. **Why**: today a `<Tab>` on an unreachable share is
indistinguishable from a `<Tab>` that found nothing — in run b the text did not change
either, and the two look the same unless you are watching the right eight pixels.
**Size**: a design question — which of filer's three ways of saying "waiting" this belongs to.

**4. `<F12>` should leave the URL where the run can read it.** The only trace it leaves is
`toast: Opened a bug report in your browser`; the URL goes nowhere unless opening failed
(`app.rs:3719`). So an unattended run cannot check what was reported, and the x64 table's
own re-test item for this key can only say "a browser opened". **What should change**: put
the URL on the `toasts:` log line, or a `report:` line in `FILER_KEYS_DONE`. **Why**: it is
the one key whose effect leaves the program entirely, and it is currently the one key whose
effect cannot be read back. **Size**: a line, and it is independent of however Q62 lands.
