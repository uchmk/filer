## Proposals

### proposal 1 — `<S-Enter>` の picker に、どのルールから来たオープナーかを出す

32.17 で `prepend_rules` と `append_rules` と `rules` の 3 つから openers が並んだとき、
picker は `Prepended opener | Middle opener | Appended opener` と**名前と run だけ**を並べる。
並び順は正しいが、**なぜその順なのかは画面に無い**。設定を書いている最中は「自分の prepend が
効いているのか、それとも たまたま `rules` の先頭なのか」が知りたい。

- **どうするか**: picker の右の注記（今は run の文字列が入っている所）に、
  `(prepend_rules)` / `(rules)` / `(append_rules)` を足す。`pick:` の `details` に 1 語足すだけ。
- **なぜ**: ルールが 3 系統に増えた（v0.78.6）ことで、順番を確かめる手段が「別のオープナーを
  一時的に消す」しか無くなった。設定を書く人全員に効く。
- **大きさ**: 1 関数。`openers_for` が名前を返すときに出どころを添える形にすれば、`exec.rs` と
  `app.rs` の picker を作る所の 2 か所。

### proposal 2 — ペインのシェルが起動に失敗したとき、`filer env` にもそう残す

1.40 の前半で `nosuchshell` を指したあと、`filer env` の `Terminal pane` は
`not opened in that run` になる。**開こうとして失敗したのか、そもそも開かなかったのかが区別できない。**
トーストは消えてしまうし、無人の実行では誰も見ていない。

- **どうするか**: `Terminal pane : failed — \`nosuchshell\` not found on PATH` のように、
  最後の失敗を 1 行で残す。
- **なぜ**: ペインが開かない、という報告が来たときに最初に見るのが `filer env` で、そこに
  「開かなかった」としか書いていないと、設定を見に行く手がかりが無い。1.40 がまさにその状況を作る行。
- **大きさ**: `runinfo` に 1 フィールド、`envreport.rs` に 1 行。

### proposal 3 — `FILER_TERM_SHELL` に引数も渡せるようにする（または `FILER_TERM_ARGS`）

1.37 の (b) で、OSC 133 でプロンプトを印す shell を用意したかったが、`FILER_TERM_SHELL` は
**プログラム名だけ**で、`[term] args` を捨てる（Q51、#190）。結局 `FILER_CONFIG_HOME` を
scratch のフォルダに向けるしかなく、**持ち主の設定（opener も keymap も theme も）を全部失った**
状態で測ることになった。役割定義が「別のシェルで試すのに `FILER_CONFIG_HOME` を空のフォルダへ
向けなくて済むように `FILER_TERM_SHELL` がある」と書いているのに、引数が要る瞬間にその利点が消える。

- **どうするか**: `FILER_TERM_ARGS`（空白区切り、または `;` 区切り）を足すのが素直。
  `FILER_TERM_SHELL` 自体をコマンドラインとして解釈する案もあるが、
  「値全体がプログラム（空白を含むパスも込み）」という今の規則を壊すので、別の変数のほうがよい。
- **なぜ**: ペインの行（1 節、8 節、29 節、39 節）はどれも「このシェルで、この起動の仕方で」を
  試す。引数の要らないシェルは実際には少ない（`-NoProfile`、`-l`、`--norc`）。
  テストのためだけでなく、ペインだけ別の起動の仕方にしたい人にも効く。
- **大きさ**: `TermCfg::take_env` の近くに 1 つ分岐を足し、`envreport.rs` の `shell_source` に
  出どころを 1 行足す程度。`CONFIG_VARS` / `filer env` が挙げる環境変数の一覧にも追加が要る。
