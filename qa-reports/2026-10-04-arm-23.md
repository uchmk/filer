## Findings

### 1. After `<Tab>` in the `cd` prompt, typing is silently lost

The field loses focus and is not given it back. Keys that the keymap owns still work
(`<Esc>` closed the prompt, `<Enter>` submitted and the tab moved), so the window looks alive —
it is only the characters that go nowhere, and the caret disappearing is the only sign.

| run | what was typed, then `<Tab>`, then `z` | `input:` at the end | `z` landed |
| --- | --- | --- | --- |
| 23-4d | `\\192.168.0.150\Backup\fil` (share, not yet listed) | `…\Backup\filer-s23\z` | **yes** |
| 23-4i | `C:\…\run-20261004-050207\s2` (local, cached) | `C:\…\s23\` | no |
| 23-4g | `\\192.168.0.150\Backup\zzz` (share, no match) | `\\192.168.0.150\Backup\zzz` | no |
| 23-4h | `C:\…\s23\zzz` (local, no match) | `C:\…\s23\zzz` | no |
| 23-4c | `\\192.168.0.231\share\fi` (dead host, still waiting) | `\\192.168.0.231\share\fi` | no |
| 23-4f | the same, `z` pressed **50 s later**, after the error toast | `\\192.168.0.231\share\fi` | no |

So it is not about the wait: 23-4f typed long after the completion had given up, and the
character was still lost. The one case that works is the one where the answer comes back from
the scan pool a frame or more after the `<Tab>`.

**Not an artefact of `--keys`.** The same thing happens with messages posted to filer's own
window (`WM_KEYDOWN`/`WM_KEYUP` for `VK_TAB` with the scan code in `lParam`, then
`WM_KEYDOWN` + `WM_CHAR` + `WM_KEYUP` for `z`), `23-4-realkeys/`:

- `a-before-tab-row.png` — `Change directory: C:\…\run-20261004-050207\s2` with the caret after `s2`
- `b-after-tab-row.png` — `…\s23\`, **no caret**
- `c-after-z-row.png` — identical to the one before it; the `z` left no mark

**Where it comes from.** `App::apply_completion` (`src/app.rs`) ends with
`ov.initial_selection = Some(…)` and `ov.focused = false`, and `ui::overlay::input`
(`src/ui/overlay.rs:196`) turns that into `resp.request_focus()` on the next frame it draws.
Two ways out of that:

- `complete_input` finds the directory in `self.cache` and calls `apply_completion`
  **in the same frame as the `<Tab>` event**, so egui's own tab-focus navigation moves focus on
  at the end of that frame, after the `request_focus()`. The cache holds the cwd, its parent and
  everywhere the tab has been, so this is the ordinary local completion.
- `hits.is_empty()` returns early, and the error branch that clears `pending_completion`
  (`src/app.rs:1660`) never calls `apply_completion` at all — so `ov.focused` stays `true` and
  nothing asks for focus back.

Proposal 1 says what I think should change.

### 3. `<Tab>` cannot complete a share name on a host

```
input: \\192.168.0.150\Ba   ->  <Tab>  ->  input: \\192.168.0.150\Ba   (unchanged)
toast: Ba: ネットワーク名が見つかりません。 (os error 67)
```

`completion_target` splits this into dir `\\192.168.0.150` and prefix `Ba`, and the scan pool
is asked to `read_dir` a bare host, which Windows refuses with error 67. filer *can* list a
host's shares — that is all of section 31, and `g<Space>\\192.168.0.150<Enter>` in this run gave
`cwd: \\192.168.0.150` with `Backup`, `backup-user`, `cache`, `VR_Video` and a header of
`4 items` (`23-hosts/shares.png`) — so the enumeration exists; completion just does not reach
for it. The user-visible
cost is doubled by finding 1: the failed `<Tab>` also kills typing, so the prompt is dead and
the only way on is `<Esc>`.

## Proposals

### 1. Give the prompt its focus back after every `<Tab>`, not only after a late answer

- **What I ran into**: finding 1. Completing a local path and then typing one more character is
  the normal way to use `g<Space>`, and the character vanishes. I lost several minutes to it
  before I realised the field was dead rather than the key being wrong.
- **What should change**: set `ov.focused = false` in `complete_input` itself — on every path
  through it, including the cache hit, the empty-hits return and the listing that failed — rather
  than only at the end of `apply_completion`. And make the request outlive egui's tab navigation
  in the frame the `<Tab>` arrives in: either consume the `Tab` event before egui sees it, or
  re-request focus on the frame *after* the one that completed.
- **Why**: it is silent. Nothing is said, nothing is logged, and `FILER_KEYS_DONE` reports a
  perfectly healthy `overlay: input` with the right `input:` text — the only sign is a caret
  missing from a picture. A prompt that eats what you type is worse than one that refuses to
  complete.
- **How big**: a few lines in `complete_input`, plus one decision about where to take the `Tab`
  event. The decision is the work, not the code.

### 2. The waiting `…` is drawn in the border colour and is nearly invisible

- **What I ran into**: I read `23-4c/waiting.png` at full size and concluded the `…` had not been
  drawn at all. It had — `ui/overlay.rs:217` paints it in `theme_border`, which on the dark theme
  is a few values off the background. I only saw it after cropping the right end and scaling it 4×.
- **What should change**: paint it in `theme.fg`, or in the accent the prompt's own title uses.
- **Why**: its whole job is to say "the key did something, wait" (the comment above it says so).
  A mark you have to zoom into does not do that job, and on a 42-second wait it is the only thing
  on screen that distinguishes "working" from "broken".
- **How big**: one line.

### 3. Offer a host's shares as completions

- **What I ran into**: finding 3. Typing `\\192.168.0.150\` and pressing `<Tab>` is the first
  thing anyone does with a server, and it gives an error instead of `Backup`, `backup-user`,
  `cache`, `VR_Video`.
- **What should change**: in `complete_input`, when the directory part of the text is a bare
  `\\host`, ask for the share listing filer already builds for section 31 instead of
  `read_dir`-ing the host.
- **Why**: without it, a share has to be typed exactly, with no help, and a typo costs the
  42-second timeout seen in 23.3. The listing code exists; completion just does not call it.
- **How big**: one branch in `complete_input` pointing at an existing function.

### 4. Put the focused field in `state_report`

- **What I ran into**: finding 1 was invisible to `FILER_KEYS_DONE`. `overlay: input` was right,
  `input:` was right, `toast:` was right — and the prompt was dead. I found it only because a
  character I typed afterwards did not appear in `input:`, and confirmed it from a caret missing
  in a picture.
- **What should change**: a `focus:` line — `list`, `prompt`, `pane`, `overlay` — in
  `state_report` (`src/main.rs:999`). The window's own idea of where the keys are going.
- **Why**: "which widget has the keyboard" is exactly the kind of thing a real-machine run has to
  prove and currently cannot, except by pressing another key and seeing what happens. Every
  section that drives a prompt (23, 30, 31, 24) would be able to assert it directly, and a
  regression like finding 1 would show up as a changed line rather than a missing caret.
- **How big**: one line in `state_report`, plus whatever it takes to read egui's focus id back.
