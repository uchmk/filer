### Finding 1 — `<F12>` says "Opened a bug report in your browser" whether or not one opened

`exec::open_url` is `open::that_detached`, and the `open` crate's
`shellexecute-on-windows` feature is **off** in this tree (`Cargo.toml` has
`open = "5"`; `Cargo.lock` lists `open`'s dependencies as `is-wsl` and `libc` only, and
`dunce` — which that feature pulls in — is not in the lockfile at all). Without it,
`that_detached` on Windows walks a list of launchers and returns `Ok(())` **as soon as
one of them spawns**. The first launcher is

```
powershell.exe -NoProfile -NonInteractive -Command <open's own script>   (OPEN_RS_TARGET=<the url>)
```

and that script's last line is `Start-Process -FilePath $env:OPEN_RS_TARGET`. So the
one thing that can go wrong in the real world — the association that `Start-Process`
resolves — happens **after** the only thing filer looks at. `powershell.exe` is in
System32 on every Windows, so it always spawns, so `open_url` always returns `Ok`, so
`app.rs:3721` always takes the `Ok(())` arm: the success toast, and no link on the
clipboard.

I could not break this machine's `https` association (it is `ChromeHTML` through the
hash-protected `UserChoice` key, and a run nobody is watching should not touch it), so
I put a stand-in in the launcher's place: a 15-line Rust program compiled to
`powershell.exe` in a directory holding its own copy of `filer.exe`, which logs what it
was asked to do and **exits 1** — which is what the real `powershell.exe` does when
`Start-Process` throws under `$ErrorActionPreference = 'Stop'`.

```
filer.exe <scratch>\s26 --keys "<Wait:1200><F12><Wait:3000><Shot:f12-decoy>"
```

`decoy-b1.log` (evidence) — the decoy was the process filer started, and it got the
whole report in its environment:

```
ran C:\...\run-20261004-040207\decoy\powershell.exe
  OPEN_RS_TARGET=https://github.com/uchmk/filer/issues/new?template=bug_report.yml&version=filer%200.73.46%20%28aarch64%29&os=OS%3A%20Windows%2011%20Home%2026H1%20%28build%2028000.2956%29%0AOS%20arch%3A%20aarch64%0AProcess%20arch%3A%20aarch64
  args=["-NoProfile", "-NonInteractive", "-Command", "...$ErrorActionPreference = 'Stop'...Start-Process -FilePath $env:OPEN_RS_TARGET..."]
```

What filer said, from `FILER_KEYS_DONE` (`done-b1.txt`):

```

```

What actually happened: nothing. Chrome process count 35 before and 35 after, its
window title `New issue - Google Chrome` from the previous run unchanged, and the
clipboard still held the sentinel `SENTINEL-arm26-runB` that I armed before the key —
so the URL was not saved anywhere either. **The report is gone and the program says it
was delivered.**

That is exactly the state 26.8 and 26.10 describe the precondition for, and in it the

Same call, same blindness, in the other place it is used: `exec::open_default`

## Findings

1. **`<F12>` reports success when no browser opened** (above). A broken or missing
   `https` association, a PowerShell blocked by policy, a user who cancels the "how do
   you want to open this?" chooser — all of them end with the success toast and the URL
   discarded. One line fixes it: `open = { version = "5", features =
   ["shellexecute-on-windows"] }`, which makes `that_detached` call `ShellExecuteExW`
   and report what it returns. `exec::open_default` is the same call and would be fixed
   with it; both want a re-test afterwards (26.8, 26.10, and the openers in 32).
2. **TESTING.md 26.8 and 26.10 name a precondition that cannot produce the behaviour
   they expect** — and cannot be set up on a real machine without rewriting a
   hash-protected `UserChoice` key. They should be split: one row for "a launcher that
   cannot start" (what I measured, and what passes today), one for "the association is
   broken" (what fails today, and what Finding 1's fix would settle).
3. Minor, not filer's doing: the `os error 216` text comes back from Windows
   localized and with `%1` unexpanded, so the toast reads
   `このバージョンの %1 は…`. It stays readable because filer's own words lead the line.

## Proposals

1. **Stop guessing that the browser opened.** `open::that_detached` on Windows reports
   on the launcher process, not on the launch, so the one toast in filer that is a
   promise to the user ("Opened a bug report in your browser") is the one it cannot
   keep. Turn on `open`'s `shellexecute-on-windows` feature so `ShellExecuteExW`'s
   result is the answer. Size: one line in `Cargo.toml` plus a re-test of 26.8 / 26.10
   / 32. Cost today: a report that was never filed, and nothing left on the clipboard
   to file it with.
2. **Fill in the one other field filer knows: the keys.** The form asks for
   `再現するキー操作` right under what went wrong (`pasted-form.png`), and a report is
   abandoned over exactly this kind of lookup — the reason the version and OS fields are
   pre-filled at all. filer already keeps a toast log (`app.toast_log`, which
   `FILER_KEYS_DONE` prints as `toasts:`); a small ring of the last ~20 keys, plus the
   newest error toast, would turn `<F12>` into a report that needs only a sentence of
   prose. Size: a ring buffer and one more URL parameter, plus a field id in
   `bug_report.yml`. (A report filed from a run like this one would have carried
   `<F12>` and the error toast itself.)
3. **`filer.com` is not what a local build produces.** `windows-role.md` and the README
   speak of `filer.com` beside `filer.exe`; `cargo build --release` writes
   `filer-com.exe`, and `.\target\release\filer.com env` fails with "not recognized" —
   which is how this run started. Either have the build (or `fetch-conpty.ps1`, which
   already stages the release layout) drop a `filer.com` copy next to `filer.exe`, or
   say in the role file that the local name is `filer-com.exe` and only the zip has the
   other. Size: a line either way; it costs every new session on this machine one
   confused command.
