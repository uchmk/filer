## 32.20 -- a `;` line with an operator and no placeholder gets no path

Folder `q82\` with `a.txt` and `b.log`; every run's `hovered:` read `…\q82\a.txt`. Each run was

`out.txt` holds `hello` alone, with no path at the end; `;echo %*` gets the path. The pipe line's
`launched:` ends at `>list.txt`, and `list.txt` holds `a.txt`.

**A stray-keystroke run, not counted (r3).** The first `echo %* >p.txt` run came out as
`launched: 20496 echon "R:\…\q82\a.txt" >p.txat` (toast ``Open failed: `echon` was not found``): an `n` and an
`a` that the script does not contain landed between the typed keys. Three repeats (r3b, r3c, r3d) of the
same script were clean. Right afterwards `GetLastInputInfo` said the last real input was 30 s earlier and the
foreground window was `Claude`, so someone was at the keyboard, and filer's window, which comes to the
front when it opens, took two of their keystrokes. This is the machine, not the row; see proposal 1.

## Proposals

1. **A `--keys` run should not take keys from the keyboard.** What I ran into: r3 above -- two physical
   keystrokes from whoever was at the desk landed inside the scripted line, and the run ran `echon`. Had
   the stray key been `d` or `<Enter>` in the list rather than in a prompt, it would have acted on a file.
   What should change: while a `--keys` script is still running, drop real keyboard (and mouse-button)
   events, or open the window without activating it (`with_active(false)`), and say in the state file
   when one was dropped (`dropped: 2 keys from the keyboard`). Why: the unattended runs share the owner's
   desktop, so this will happen again, and a result built on a mixed run is quietly wrong; the
   `dropped:` line would also let a run tell a stray-key run from a filer bug without guessing. Size: a
   function in the input path, gated on the script not being finished.
2. **`filer env`'s long-key rule could also cover the `Tools` section's long names consistently.** What I
   ran into: in the same output, `Tools` already puts `C:\Program Files (x86)\sakura\sakura.exe` on its own
   line with its value below, but at an indent of 12 there against 15 in `Config`. What should change:
   one indent for both sections' wrapped values. Why: the two rules read as two different layouts in one
   screen. Size: a line.
