mid-run with `<Now><Shot:sN><Now><State:sN>` (about 20 ms apart) or with `<Wait:400>` between them.
The percentages and times were read from the status bar of each shot; the file counts come from the `job:` line
of the matching `<State:>`.

**100 MB file + 5000 one-line files** (`6.17-mixed\strip.png`). Total work with
`FILE_COST` = 64 KiB is 104.9 MB + 5001 × 64 KiB ≈ 432.6 MB:

| shot | `job:` files | bar | expected by files+bytes | bytes alone |
| --- | --- | --- | --- | --- |
| s7 | 21 (big file done) | 25% | 24.6% | ≈ 100% |
| s9 | 139 | 26% | 26.4% | ≈ 100% |
| s19 | 613 | 34% | 33.5% | ≈ 100% |
| s27 | 1104 | 41% | 41.0% | ≈ 100% |
| s39 | 1834 | 52% | 52.0% | ≈ 100% |

The copy ended 5001 / 5001. The bar moves with the files, not the bytes.

Its time left, though, read `0s` from s19 (34%) to s40 (52%). Between s19 (`14:58:22.104`) and s39 (`22.604`)
1221 files went in 0.5 s, so about 3 170 files, roughly a second, were still to come. The cause is
`Task::eta` (`app.rs:566`): `by_pace` only counts once 2 s have passed. Before that the time left is
bytes alone, and the bytes left were a few KB. The row's case, seconds of copying still to come,
is the 40 000-file run below, and there the time left is right.

**40 000 one-line files, source on R:, destination on C:** (`6.17-many\strip.png`, 2 500 files/s,
about 16.5 s). The bar tracks the count (s3 1065 → 2%, s20 19103 → 48%, s30 29541 → 74%).
The time left reads `17s` at s3, then counts down to `4s` at s30. The copy really ended
about 15.8 s after s3 and about 4.2 s after s30 (state file times; the last file landed between
s30 and `end`). Nothing read `97% … 1s`.

**One 3 GB file** (`6.17-big\strip.png`, 2.3 G/s). The bar climbs evenly with time
(s5 4%, s15 24%, s30 47%, s45 70%, s60 94%, about 21 ms apart). The `job:` line stays at
`0/1 files` all the way, so the bar moved on bytes, as before. The 100 MB single-file
run (`6.17-onebig`) finished inside 40 ms, before any reading.

Side note, not a failure of this row: at s15 of the 3 GB run, the time left read `0s`
with about one second still to go. `fmt_duration` floors (`as_secs`), so 0.97 s prints as
`0s` (proposal 2).

### Proposals

1. **Don't scan the parent column of a jump that has not landed yet, or drop its
   failure when the jump itself fails.** What I ran into: finding 1, two toasts for one typo.
   What should change: when the `ScanResult::Failed` for a pending jump undoes the jump (`app.rs`
   near 1801), it should also remove a toast from the same jump's parent scan, or the parent
   scan should wait for the listing. Why: the second toast names a path the user never typed. It also
   pushes the first toast, the one that tells you what happened, out of the top line. Size: small.
2. **Don't show `0s` for a job that is clearly not done.** What I ran into: the 3 GB copy
   read `24% … 0s` with about a second still to go. The 100 MB + 5000 files run read
   `34% … 0s` through `52% … 0s` for about a second. There are two causes: `fmt_duration` floors (0.97 s
   prints as `0s`), and in the first 2 s `Task::eta` uses bytes alone, which for small
   files is near zero. 6.17 checks for `1s` while seconds remain; this is the same mistake one unit lower.
   What should change: round the time left up (`as_secs_f64().ceil()`), and leave it out
   until `by_pace` can count, rather than show the bytes-only figure. Why: `0s` reads as
   "done", and the bar plainly is not. Size: a few lines.
3. **Give 32.19 a way to say which editor was used.** What I ran into: the row says
   "an editor opener (サクラ, Notepad)", but on this machine `.txt` goes to nvim first, in a
   console. The PID part works the same either way. Starting Sakura would have put a
   second Sakura next to the owner's unsaved one, and starting Notepad would touch the owner's restored tabs.
   What should change: the row should say "the first `edit` opener, whatever it is". Why: a run
   should not have to choose between skipping the row and risking the owner's editors.
   Size: a row rewrite.
