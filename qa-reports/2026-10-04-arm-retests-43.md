## 見つけたこと

1. 不具合は無い。v0.73.64 の高さの計算は、実機の 1360 x 860 の窓でちょうど 12 px になっている。
2. 覚え書き: `--keys` のスクリプトを `q` で終えると、`FILER_KEYS_DONE` の状態の行は**終了時の状態**になるので
   `overlay: none` と書かれる。オーバーレイが開いている状態を読みたい run は `q` を付けずに終え、
   done ファイルが現れるのを待ってから読み、あとで `filer.exe` を止めることになる（この run は 2 本ともそうした）。
   `Start-Process -Wait` が使えるのは `q` で終わるスクリプトだけ。提案 3 はここから。
3. 覚え書き: パネルの本文は `FILER_KEYS_DONE` に出ないので、半分 1 は画面の画像から文字を読んだ。
   `pick:` の行がピッカーに対してやっていることと同じものが confirm には無い。提案 2 はここから。

## Proposals（3 件）

### 提案 1: Report a bug のボタンに `<Enter>` も書く

- **踏んだこと**: パネルのボタンは `[o] Open the form in your browser` / `[c] Copy the link` / `[n] Cancel` の 3 つで、
  **`<Enter>` がどれに当たるかはどこにも書いていない**。この run の 2 本目は `<Enter>` を押しただけで
  ブラウザが開き、タブが 1 本増えた（上の半分 3）。TESTING.md 26.1 自身が「`<Enter>`（または `o`）」と書いているのに、
  画面だけを見た人には読み取れない。
- **どう変えるべきか**: 既定の選択肢のラベルに入れる。`[o] / <Enter>  Open the form in your browser` のように、
  最初の選択肢にだけ `<Enter>` を足す（`confirm()` のラベル作りは `format!(" [{k}] {l} ")` の 1 行なので、
  `ConfirmOverlay` に「どれが `<Enter>` か」を持たせて、その 1 つだけ書き方を変える）。
- **なぜ**: `<Enter>` が走らせるのは**外に出ていく動作**（ブラウザが開く）で、確認の箱がそもそも Q62 で入ったのは
  「押した瞬間に外へ出る」のをやめるためだった。その箱の中に、押した瞬間に外へ出るキーが隠れている。
  ごみ箱の確認など他の confirm でも同じことが言える。
- **大きさ**: ラベル 1 か所と、どれが既定かを持つフィールド 1 つ。

### 提案 2: `FILER_KEYS_DONE` に `confirm:` の行を出す（`pick:` と同じ形で）

- **踏んだこと**: 26.1 の 3 分の 2 は「パネルに版・OS・直前のキー・描画・倍率・設定ファイルの名前が並ぶ」ことで、
  これは**文字**なのに、`FILER_KEYS_DONE` には `overlay: confirm` の 1 語しか出ない。だからこの run は
  10 行を画像から読んだ。画像から文字を読むのは認められているが、**自動で比べられない**（`filer env` の
  OS の行と突き合わせるのも手でやった）。
- **どう変えるべきか**: `state_report()` に、`pick:` / `picked:` と同じ場所で
  `confirm: <title> | <body を ' / ' でつないだもの> | [o] … [c] … [n] …` を出す。
  `app::Overlay::Pick` に対して既にやっていることを `Overlay::Confirm` にも足すだけ。
- **なぜ**: 確認の箱が出る行は 26.1 だけではない（12 のごみ箱、13 のジャンクションの質問、21 の上書き、
  45 のリンク）。どれも今は「画像を見るか、ソースを読むか」になっている。1 行増やすと、この一群が
  まとめて**文字で比べられる行**に変わる。倍率や GPU 名のように機械ごとに違う値が入るので、
  2 台のレーンの差分を見るのにも効く。
- **大きさ**: `main.rs` の `state_report()` に 5 行ほど。`pick:` の実装がそのまま手本になる。

### 提案 3: 状態を途中で書き出す `<State:name>` を `--keys` に足す

- **踏んだこと**: この run は 2 本とも、**`q` を付けずに起動して done ファイルを待ち、読んでから
  `Stop-Process` で殺した**。`q` を付けると状態の行が終了時のもの（`overlay: none`）になってしまい、
  「パネルが出ている」ことを done ファイルで言えないからだ。結果として `Start-Process -Wait` が使えず
  （役割定義が #225 で勧めている形）、ポーリングと後始末を自分で書くことになった。
  殺し忘れれば `filer.exe` が残る。
- **どう変えるべきか**: `<Shot:name>` と同じ場所に `<State:name>` を足し、押された時点の
  `state_report()` を `name.txt` として done ファイルの隣に書く。そうすれば
  `"<F12><State:panel><Shot:panel><Enter><Wait:3000>q"` の 1 本で、途中の状態も最後の状態も取れて、
  スクリプトは自分で終わる。
- **なぜ**: 今は「途中の状態」を取るたびに run が 1 本増え、プロセスの後始末が run の数だけ要る。
  `<Shot:>` が画像に対して解いた問題（「2 回起動して窓の大きさが同じであることに頼る」）が、
  状態の文字に対してはまだ解かれていない。
- **大きさ**: `keyscript::Step` に 1 つ、`Press` に 1 つ、フレームループに 1 分岐。`Shot` の実装がそのまま手本。
