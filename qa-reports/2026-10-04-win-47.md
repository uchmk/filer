## 47. 放置した窓は CPU を使わない — x64（80bb95c / 0.73.72、win レーン、無人の run）

`.claude/windows-role.md` の順番表の先頭「Re-tests of changed behaviour」に開いている行は無かったので、次の「47. an idle window uses no CPU」を進めた。
この節で開いているのは **47.1 だけ**で、x64 では #204 / #207 から失敗のまま（AMD のドライバのスレッドが 1 コアを回す）。
バックエンドや present mode の直しは `main` に入っていない（`git log` と `src/main.rs` の `NativeOptions` を見た）ので、この run では
**(1) 0.73.72 で 47 節の全行を x64 で測り直し**、**(2) TODO.md の【実機】「`Fifo` の present mode やフレームの遅延を変えて、この機械で試すビルドを作る」を

### 実験: present mode とフレームの遅延（TODO.md の【実機】の項目）

`src/main.rs` の `NativeOptions` の直後に、`FILER_EXP_PRESENT`（`fifo` / `fiforelaxed` / `mailbox` / `immediate` / `autonovsync`）と
`FILER_EXP_LATENCY` から `options.wgpu_options.surface` を決める 15 行を足してビルドし、exe を scratch に写してから **`git restore src/main.rs` で戻した**
（この PR にコードの変更は無い）。既定は egui-wgpu 0.36.2 の `SurfaceConfig::LOW_LATENCY`（`AutoVsync`、遅延 1）。

| present mode | 遅延 | Vulkan（既定） | DX12 |
| --- | --- | --- | --- |
| `AutoVsync`（今の既定） | 既定（1） | 10.016 s | 9.969 s |
| `Fifo` | 既定 | 9.984 s | 9.969 s |
| `FifoRelaxed` | 既定 | 10.016 s | **起動して 5 秒以内に終了**（読みではない） |
| `Mailbox` | 既定 | **起動して 5 秒以内に終了**（読みではない） | 9.984 s |
| `Immediate` | 既定 | 10.000 s | 10.016 s |
| `AutoNoVsync` | 既定 | 10.016 s | 9.969 s |
| `AutoVsync` | 2 | 10.016 s | 9.938 s |
| `AutoVsync` | 3 | 10.016 s | 9.984 s |
| `Fifo` | 2 | 9.984 s | 10.000 s |

- 回っているのは毎回同じ 1 本（Vulkan は `amdvlk64.dll+0x2F3DA4C`、DX12 は `amdxc64.dll+0x1298D0`）。
- **present mode もフレームの遅延も効かない。**動いた組み合わせは全部 1 コアを使う。0 と出た 2 つはプロセスが消えていた（`out-exp-vk-mailbox-latdef.txt`
  と `out-exp-dx12-fiforelaxed-latdef.txt`: 窓のタイトルが空、スレッドもモジュールも読めず、`Stop-Process` が「プロセスが見つかりません」）。
  そのドライバがその present mode を持たず、egui-wgpu / wgpu が起動時に止まったと読める。
- つまり、TODO.md の項目の「`Fifo` の present mode やフレームの遅延を変えて、この機械で試す」の答えは「**どれでも変わらない、GL だけが 0**」。
  スレッドは起動直後から回る（#207）ので、スワップチェーンの出し方より前、デバイスかインスタンスを作った時点で始まっている公算が高い。

### 比較: 同じ機械の別の wgpu アプリ（結論なし）

WezTerm 20240203（`C:\Program Files\WezTerm`）を scratch の設定ファイル（`--config-file`、持ち主の設定は読まない）で `front_end = 'WebGpu'` にして、
同じ測り方をした。`enumerate_gpus()` は Vulkan・DX12 の両 GPU と GL を列挙し、`webgpu_power_preference` を `LowPower` / `HighPerformance`、
`webgpu_preferred_adapter` を Vulkan の dGPU にしても、**10 秒で 0.000〜0.031 s** だった。ただし 3 回とも、ドライバのスレッドは
`atio6axx.dll+0x12A9F10`（AMD の GL ドライバ）だけで `amdvlk64.dll` のスレッドが無く、**Vulkan で描いていた証拠が取れなかった**ので、
「別の wgpu アプリは Vulkan でも回らない」とは言えない。WezTerm が作ったログ（`%USERPROFILE%\.local\share\wezterm\` の自分の PID の 5 ファイルと
`gui-sock` 1 つ）は消した。必要な行は `out-wez-*.txt` に写してある。

### 見つけたこと

1. **x64（AMD）の 47 節は、0.73.72 でも既定のバックエンドで全行が失敗する**（上の表）。47.1 は `[ ]` のまま。47.2 / 47.3 / 47.5 の `[x]` は ARM64 の印で、
   x64 では同じドライバのスレッドのために 10 s / 10 s。GL ではすべて 0。
2. **present mode（5 種）とフレームの遅延（1〜3）のどれでも止まらない**（実験の表）。TODO.md の【実機】の項目はこれで答えが出たので閉じてよい。
3. **使えない present mode を選ぶと、filer は何も言わずに起動直後に終わる**（Vulkan の `Mailbox`、DX12 の `FifoRelaxed`）。今の filer は present mode を
   変えないので不具合ではないが、設定にするなら効く前提で作ってはいけない（提案 2）。

### Proposals（3）

1. **バックエンドを `filer.toml` で選べるようにする**（例 `[ui] backend = "gl"`）。
   - 何があったか: この機械では、何もしていない filer が Vulkan と DX12 で 1 コアを使い続け、`WGPU_BACKEND=gl` でだけ 0 になる（この run の 47 節の全行）。
     今それを避ける方法は、filer を起動する全部の経路（スタートメニュー、`filer.com`、エクスプローラーのダブルクリック）に環境変数を通すことしかない。
   - 変えるもの: 設定のキーを 1 つ足し、`NativeOptions.wgpu_options.wgpu_setup` のバックエンドに渡す。`filer env` の `Adapter` 行は今のままで効いたバックエンドが読める。
   - なぜ: ノート PC ならバッテリー、デスクトップでもファンと電気代。持ち主の x64 機は AMD なので、持ち主自身がいちばん得をする。
   - 大きさ: 関数 1 つと README の 1 行。既定を Windows で GL にするかどうかは持ち主の判断（GL は ARM64 の Windows に無いことがある）。
2. **present mode を設定にするなら、サーフェスが持つものに落とす。**
   - 何があったか: 実験ビルドで `Mailbox`（Vulkan）と `FifoRelaxed`（DX12）を選ぶと、窓が出ないまま 5 秒以内にプロセスが消え、何も言わなかった。
   - 変えるもの: 選んだ mode が `surface.get_capabilities().present_modes` に無ければ `AutoVsync` にして、`filer env` の警告に 1 行出す。
   - なぜ: 黙って起動しないのは、設定ファイルの 1 行の打ち間違いで filer が使えなくなる形で、原因にたどり着けない。
   - 大きさ: 設定を足すときに一緒に数行。今は設定が無いので何もしなくてよい。
3. **`FILER_KEYS_DONE` に、描いているバックエンドとアダプタを出す**（`adapter: AMD Radeon RX 9070 XT (Vulkan, DiscreteGpu)`）。
   - 何があったか: この run の 28 回の起動で、どのバックエンドで動いたかは、読み込まれた DLL（`amdvlk64.dll` か `amdxc64.dll` か `atio6axx.dll` か）と
     回るスレッドの開始アドレスから推すしかなかった。`filer env` の「Last run」は終了した後の前回の分なので、同じ回の状態ファイルと並ばない。
     WezTerm との比較が結論なしに終わったのも、まさに「どのバックエンドで描いているか」が外から読めなかったため。
   - 変えるもの: 状態ファイルに 1 行。値は `runinfo` が既に持っている。
   - なぜ: 47 節のような GPU 依存の行で、測った数字がどのバックエンドのものかを同じファイルで言える。
   - 大きさ: 1 行。
